1 Designprinsipper og SOLID

1.1 Liskov-substitusjonsprinsippet

I bibliotek-systemet finnes klassen Laan som representerer et utlån. Et utlån kan fornyes. En utvikler har lagt til Referanselaan for bøker som bare kan brukes på lesesalen:

public class Laan {
    protected LocalDate forfallsdato;

    public void forny() {
        forfallsdato = forfallsdato.plusWeeks(2);
    }
}

public class Referanselaan extends Laan {
    @Override
    public void forny() {
        throw new UnsupportedOperationException("Referanseverk kan ikke fornyes");
    }
}
  • a) Forklar hvorfor denne koden bryter Liskov-substitusjonsprinsippet (LSP).
  • b) Foreslå en bedre design som unngår problemet. Skissér koden.

(1–2 avsnitt + kode)

a) Bruddet:

LSP sier at en subtype skal kunne brukes overalt der supertypen forventes, uten at programmet oppfører seg feil. Her arver Referanselaan fra Laan, men kan ikke oppfylle kontrakten til forny() – den kaster en exception i stedet. Kode som tar inn en Laan og kaller forny() (f.eks. en «forny alle lån»-funksjon) vil krasje hvis den får et Referanselaan. Subtypen er altså ikke en ekte erstatning for supertypen.

b) Bedre design:

Skill ut det som faktisk kan fornyes i et eget grensesnitt, slik at bare lån som støtter fornying implementerer det:

public interface Fornybar {
    void forny();
}

public abstract class Laan {
    protected LocalDate forfallsdato;
    // felles oppførsel for alle lån
}

public class StandardLaan extends Laan implements Fornybar {
    @Override
    public void forny() {
        forfallsdato = forfallsdato.plusWeeks(2);
    }
}

public class Referanselaan extends Laan {
    // implementerer ikke Fornybar – kan ikke fornyes
}

Nå kan kode som fornyer lån ta inn Fornybar i stedet for Laan, og Referanselaan kan rett og slett ikke sendes inn der. Feilen fanges av kompilatoren i stedet for å bli en kjøretidsfeil.

Inntil 6 poeng. a) 3 poeng – må forklare at subtypen ikke kan erstatte supertypen, og peke på konkrete konsekvenser (kode som kaller forny() krasjer). b) 3 poeng – må foreslå en løsning som skiller ut fornybar oppførsel (grensesnitt), eller på annen måte unngår at Referanselaan arver en kontrakt den ikke kan oppfylle.

1.2 Grensesnittseparasjon (ISP)

Alle ting man kan låne i biblioteket implementerer dette grensesnittet:

public interface Biblioteksobjekt {
    void laanUt(Medlem medlem);
    void leverInn();
    int antallSider();
    void spillAv();
    int spilletidMinutter();
}

Grensesnittet implementeres av Bok, Lydbok og Film. En Bok har ingen spillAv(), og en Film har ingen antallSider().

  • a) Hvilket SOLID-prinsipp brytes, og hva blir konsekvensen for klassene som implementerer grensesnittet?
  • b) Del opp grensesnittet slik at problemet løses. Vis hvilke grensesnitt Bok og Lydbok da ville implementert.

(1–2 avsnitt + kode)

a) Prinsipp: Interface Segregation Principle (ISP) – ingen klasse skal tvinges til å være avhengig av metoder den ikke bruker. Her må Bok implementere spillAv() og spilletidMinutter() selv om de er meningsløse, og Film må implementere antallSider(). Resultatet blir tomme metoder eller metoder som kaster exceptions – som igjen lett fører til LSP-brudd.

b) Oppdelt løsning:

public interface Laanbar {
    void laanUt(Medlem medlem);
    void leverInn();
}

public interface Trykt {
    int antallSider();
}

public interface Avspillbar {
    void spillAv();
    int spilletidMinutter();
}

public class Bok implements Laanbar, Trykt { /* ... */ }

public class Lydbok implements Laanbar, Avspillbar { /* ... */ }

Hver klasse implementerer nå bare det den faktisk støtter. Film ville implementert Laanbar og Avspillbar.

Inntil 5 poeng. a) 2 poeng – må navngi ISP og forklare konsekvensen (tomme metoder / metoder som ikke gir mening). b) 3 poeng – må dele grensesnittet i mindre, sammenhengende grensesnitt og vise riktig bruk i minst to klasser.

1.3 Enkeltansvarsprinsippet

Forklar kort hva Single Responsibility Principle (SRP) betyr. Beskriv så en Medlem-klasse i bibliotek-systemet som ville brutt prinsippet, og hvordan du ville delt den opp.

(1 avsnitt)

SRP sier at en klasse skal ha én grunn til å endres – altså ett ansvar. Hvis en klasse gjør flere uavhengige ting, vil endringer i én del kunne påvirke de andre.

En Medlem-klasse som bryter SRP kunne f.eks. både holde på medlemsdata (navn, lånekortnummer), lagre seg selv til databasen (lagreTilDatabase()), og sende e-postvarsler (sendPurring()). Det er tre grunner til å endre klassen: endret datamodell, endret database, og endret varslingsmåte.

Bedre: Medlem holder kun data, MedlemRegister tar seg av lagring, og VarslingsTjeneste tar seg av e-post.

Inntil 4 poeng. 2 poeng for korrekt forklaring av SRP («én grunn til å endres»), 2 poeng for et konkret eksempel på en klasse med flere ansvar og en fornuftig oppdeling.

2 Testing og mocking

2.1 JUnit og testoppsett

Biblioteket beregner gebyr for forsinkede bøker med denne klassen:

public class Gebyrkalkulator {
    private static final double SATS_PER_DAG = 5.0;

    public double beregnGebyr(int dagerForsinket) {
        if (dagerForsinket <= 0) {
            return 0.0;
        }
        return dagerForsinket * SATS_PER_DAG;
    }
}
  • a) Skriv JUnit 5-tester for beregnGebyr. Dekk minst: ingen forsinkelse, en vanlig forsinkelse, og grensetilfellet 0 dager.
  • b) Forklar kort hva @BeforeEach gjør, og hvorfor det er nyttig.

(kode + 1 avsnitt)

a) Tester:

class GebyrkalkulatorTest {
    private Gebyrkalkulator kalkulator;

    @BeforeEach
    void oppsett() {
        kalkulator = new Gebyrkalkulator();
    }

    @Test
    void ingenGebyrNaarIkkeForsinket() {
        assertEquals(0.0, kalkulator.beregnGebyr(-3));
    }

    @Test
    void gebyrForVanligForsinkelse() {
        assertEquals(15.0, kalkulator.beregnGebyr(3));
    }

    @Test
    void ingenGebyrPaaGrensen() {
        assertEquals(0.0, kalkulator.beregnGebyr(0));
    }
}

b) @BeforeEach: Metoden merket med @BeforeEach kjøres på nytt før hver enkelt testmetode. Det brukes til å sette opp en fersk tilstand (her: en ny Gebyrkalkulator) slik at testene er uavhengige av hverandre – ingen test arver tilstand fra en tidligere test.

Inntil 5 poeng. a) 3 poeng – tre tester med riktige assertEquals som dekker de tre tilfellene. b) 2 poeng – må forklare at @BeforeEach kjører før hver test og bidrar til uavhengige tester.

2.2 Mocking med Mockito

Klassen Laanetjeneste håndterer utlån. Den er avhengig av et BokRegister (mot databasen) og en VarslingsTjeneste (sender e-post):

public class Laanetjeneste {
    private final BokRegister register;
    private final VarslingsTjeneste varsling;

    public Laanetjeneste(BokRegister register, VarslingsTjeneste varsling) {
        this.register = register;
        this.varsling = varsling;
    }

    public boolean laanUt(String isbn, Medlem medlem) {
        Bok bok = register.finnViaIsbn(isbn);
        if (bok == null || !bok.erTilgjengelig()) {
            return false;
        }
        bok.settTilgjengelig(false);
        varsling.sendBekreftelse(medlem, bok);
        return true;
    }
}
  • a) Skriv en test med Mockito som sjekker at når boka finnes og er tilgjengelig, så returnerer laanUt true, og at sendBekreftelse faktisk blir kalt. Bruk mock(), when().thenReturn() og verify().
  • b) Forklar kort hvorfor det er en fordel å mocke BokRegister i denne testen i stedet for å bruke en ekte database.

(kode + 1 avsnitt)

a) Test:

@Test
void laanerUtTilgjengeligBok() {
    BokRegister register = mock(BokRegister.class);
    VarslingsTjeneste varsling = mock(VarslingsTjeneste.class);
    Bok bok = new Bok("978-82-05-12345-6", true);
    Medlem medlem = new Medlem("Ada");

    when(register.finnViaIsbn("978-82-05-12345-6")).thenReturn(bok);

    Laanetjeneste tjeneste = new Laanetjeneste(register, varsling);
    boolean resultat = tjeneste.laanUt("978-82-05-12345-6", medlem);

    assertTrue(resultat);
    verify(varsling).sendBekreftelse(medlem, bok);
}

b) Hvorfor mocke: En ekte database gjør testen treg, vanskelig å sette opp, og avhengig av ytre tilstand (hva som ligger i databasen akkurat nå). Med en mock bestemmer testen selv nøyaktig hva finnViaIsbn skal returnere, slik at vi kan teste logikken i Laanetjeneste isolert, raskt og forutsigbart.

Inntil 6 poeng. a) 4 poeng – riktig bruk av mock(), when().thenReturn() for å stubbe registeret, en assert på returverdien, og verify() på varslingen. b) 2 poeng – må peke på isolasjon, hastighet eller forutsigbarhet.

2.3 Prioritering av tester

Du har begrenset tid før innlevering. Hvilke deler av bibliotek-systemet ville du prioritert å skrive enhetstester for, og hva ville du nedprioritert? Begrunn valgene.

(1 avsnitt)

Prioriter: Forretningslogikk der feil får konsekvenser – gebyrberegning, regler for hvem som kan låne hva, hvor lenge et lån varer, og om en bok er tilgjengelig. Disse har mange grensetilfeller (0 dager forsinket, maks antall lån osv.) og er vanskelige å verifisere manuelt.

Nedprioriter: Trivielle gettere og settere uten logikk, ren GUI-tegning, og kode fra rammeverk/biblioteker (den er allerede testet). Slike tester gir høy dekningsprosent, men lite reell trygghet.

Begrunnelse: Tester skal gi trygghet for at det som kan gå galt fungerer – ikke bare øke et dekningstall.

Inntil 4 poeng. Søker at studenten prioriterer ikke-triviell logikk / grensetilfeller og nedprioriterer trivielle gettere, GUI og rammeverkskode – med en fornuftig begrunnelse.

3 Git, samarbeid og CI/CD

3.1 Merge-konflikt

Du skal slå sammen grenen feature/gebyrregler inn i main, men får en konflikt. Git viser dette i fila:

<<<<<<< HEAD
    public double beregnGebyr(int dager) {
        return dager * 5.0;
    }
=======
    public double beregnGebyr(int dager) {
        return dager * 4.0 + 10.0;
    }
>>>>>>> feature/gebyrregler
  • a) Forklar hva konfliktmarkørene betyr – hva er HEAD, og hva er koden under =======?
  • b) Beskriv hvordan du ville gått fram for å løse konflikten på en god måte.

(1–2 avsnitt)

a) Markørene: Koden mellom <<<<<<< HEAD og ======= er versjonen i grenen du står på (main). Koden mellom ======= og >>>>>>> feature/gebyrregler er versjonen fra grenen du slår inn. Begge grenene har endret de samme linjene, så Git kan ikke avgjøre selv hvilken som er riktig.

b) Framgangsmåte:

  • Ikke bare velg én tilfeldig – finn ut hvorfor hver endring ble gjort. Her har de to grenene helt ulik gebyrlogikk.
  • Snakk med den som lagde den andre endringen. Kanskje er den nye regelen (4.0 + 10.0) den vedtatte – eller kanskje ingen av dem er helt rett.
  • Rediger fila slik at den inneholder den riktige koden, og fjern alle konfliktmarkørene (<<<, ===, >>>).
  • Bygg og kjør testene for å bekrefte at resultatet fungerer.
  • git add på fila og fullfør sammenslåingen med en commit.

Inntil 6 poeng. a) 3 poeng – må forklare at HEAD er gjeldende gren og den andre delen er innkommende gren, og at konflikten skyldes endringer på de samme linjene. b) 3 poeng – må vise en fornuftig prosess: forstå begge endringene, kommunisere, fjerne markører, teste, fullføre commit.

3.2 Git-arbeidsflyt

Du jobber på en feature-branch med endringer som ikke er ferdige (koden kompilerer ikke engang). Plutselig får du beskjed om en kritisk feil i main som du må fikse umiddelbart. Beskriv steg for steg hva du ville gjort med Git, og forklar kort hvorfor.

(1 avsnitt eller punktliste)

  1. git stash – legger de uferdige endringene til side uten å committe halvferdig kode. (Alternativt: committe på feature-branchen som en «WIP»-commit.)
  2. git switch main og git pull – får siste versjon av main.
  3. git switch -c fix/kritisk-feil – lager en egen branch for feilrettingen.
  4. Fiks feilen, kjør testene, commit, push og lag en merge request.
  5. git switch feature/... for å gå tilbake til feature-branchen.
  6. git stash pop – henter tilbake de uferdige endringene og fortsetter der du slapp.

Poenget er å holde feilrettingen adskilt fra det uferdige arbeidet, slik at fiksen kan slås inn i main alene, uten halvferdig kode.

Inntil 4 poeng. Søker en fornuftig sekvens som tar vare på det uferdige arbeidet (stash eller WIP-commit), bytter til en oppdatert main, fikser feilen på en egen branch, og henter tilbake arbeidet etterpå.

3.3 CI/CD-pipeline

Teamet ditt setter opp en CI/CD-pipeline i GitLab for bibliotek-systemet. Beskriv minst tre stadier (stages) du ville hatt i pipelinen, hva hvert stadium gjør, og forklar hvorfor rekkefølgen på stadiene er viktig.

(1–2 avsnitt)

Eksempel på stadier:

  • build – kompilerer prosjektet. Feiler dette, er det ingen vits i å gå videre.
  • test – kjører enhets- og integrasjonstester. Fanger regresjoner før de når main.
  • analyse – statisk analyse (f.eks. SonarQube) og linting. Finner potensielle feil, kodelukt og stilbrudd uten å kjøre koden.
  • deploy – ruller ut til et test- eller produksjonsmiljø, men bare hvis alt over har gått grønt.

Hvorfor rekkefølgen er viktig: Stadiene går fra raskt/billig til tregt/dyrt, og fra grunnleggende til avansert. Det er meningsløst å kjøre tester hvis koden ikke kompilerer, og farlig å deploye hvis testene feiler. Prinsippet er «fail fast» – oppdag problemer så tidlig og billig som mulig.

Inntil 5 poeng. 3 poeng for tre fornuftige stadier med beskrivelse, 2 poeng for en god begrunnelse av rekkefølgen (fail fast – billig før dyrt, ikke deploye på feilende tester).

4 Refaktorering og kodekvalitet

4.1 Kodelukt

Se på denne metoden fra BibliotekManager:

public void behandleInnlevering(String isbn, String medlemsId, LocalDate levert) {
    Bok bok = database.query("SELECT * FROM bok WHERE isbn = " + isbn);
    Medlem medlem = database.query("SELECT * FROM medlem WHERE id = " + medlemsId);
    long dagerForsinket = ChronoUnit.DAYS.between(bok.getForfallsdato(), levert);
    if (dagerForsinket > 0) {
        double gebyr = dagerForsinket * 5.0;
        medlem.setSaldo(medlem.getSaldo() + gebyr);
        System.out.println("Gebyr lagt til: " + gebyr);
        epostServer.connect();
        epostServer.send(medlem.getEpost(), "Du har et gebyr på " + gebyr);
        epostServer.disconnect();
    }
    bok.setTilgjengelig(true);
    database.update(bok);
    database.update(medlem);
    System.out.println("Innlevering behandlet");
}
  • a) Identifiser minst tre kodelukter eller problemer i denne metoden.
  • b) Beskriv kort hvordan du ville refaktorert metoden for å rette opp problemene.

(1–2 avsnitt)

a) Problemer:

  • Lang metode / for mange ansvar: Metoden gjør databasetilgang, gebyrberegning, varsling og logging om hverandre – flere abstraksjonsnivåer i samme metode.
  • SQL-injeksjon: Spørringen bygges ved å lime inn isbn og medlemsId direkte i strengen. Det er et sikkerhetshull – bruk parameteriserte spørringer.
  • Magisk tall: 5.0 er hardkodet. Bør være en navngitt konstant (eller hentes fra Gebyrkalkulator).
  • Logging med System.out.println: Bør bruke et logge-rammeverk, ikke utskrift til konsoll.
  • Ingen feilhåndtering: Hva skjer hvis boka eller medlemmet ikke finnes (null)?

b) Refaktorering:

Trekk ut ansvar i egne klasser/metoder: et BokRegister og MedlemRegister for databasetilgang (med parameteriserte spørringer), Gebyrkalkulator for selve beregningen, og en VarslingsTjeneste for e-post. Selve behandleInnlevering bør da bli kort og bare koordinere disse – ett abstraksjonsnivå, lett å lese og å teste.

Inntil 6 poeng. a) 3 poeng – minst tre reelle problemer (lang metode / blandede ansvar, SQL-injeksjon, magisk tall, System.out, manglende feilhåndtering). b) 3 poeng – en konkret refaktorering som trekker ut ansvar i egne enheter.

4.2 Åpen–lukket-prinsippet og Strategy

Lånetiden avhenger av medlemstype:

public class Laanepolicy {
    public int laanetidDager(String medlemstype) {
        if (medlemstype.equals("STUDENT")) {
            return 28;
        } else if (medlemstype.equals("ANSATT")) {
            return 90;
        } else if (medlemstype.equals("GJEST")) {
            return 7;
        } else {
            return 14;
        }
    }
}
  • a) Hvilket prinsipp gjør denne koden vanskelig å vedlikeholde, og hva må du gjøre hver gang det kommer en ny medlemstype?
  • b) Refaktorer koden med polymorfi / Strategy-mønsteret slik at nye medlemstyper kan legges til uten å endre eksisterende kode. Skissér løsningen.

(1–2 avsnitt + kode)

a) Prinsipp: Koden bryter Open–Closed Principle – den er ikke «lukket for endring». For hver ny medlemstype må du åpne Laanepolicy og legge til en ny else if-gren. Det øker risikoen for feil i kode som allerede virker.

b) Refaktorering med Strategy:

public interface Medlemstype {
    int laanetidDager();
}

public class Student implements Medlemstype {
    public int laanetidDager() { return 28; }
}

public class Ansatt implements Medlemstype {
    public int laanetidDager() { return 90; }
}

// Laanepolicy trenger ikke lenger kjenne hver enkelt type:
public class Laanepolicy {
    public int laanetidDager(Medlemstype type) {
        return type.laanetidDager();
    }
}

Nå legger man til en ny medlemstype ved å lage en ny klasse som implementerer Medlemstype – uten å røre Laanepolicy. Koden er åpen for utvidelse, men lukket for endring. (En enum med en metode er et godt alternativ.)

Inntil 5 poeng. a) 2 poeng – må identifisere Open–Closed Principle og forklare at man må endre klassen for hver ny type. b) 3 poeng – en løsning med grensesnitt/polymorfi (eller enum med metode) der nye typer ikke krever endring i Laanepolicy.

4.3 Kobling mellom klasser

Forklar kort hva kobling (coupling) mellom klasser betyr. Hvorfor er løs kobling ønskelig, og nevn én konkret teknikk for å redusere koblingen mellom to klasser.

(1 avsnitt)

Kobling beskriver hvor mye en klasse er avhengig av en annen – hvor mye den vet om den andres indre detaljer. Ved tett kobling sprer en endring i én klasse seg lett til mange andre.

Løs kobling er ønskelig fordi det gjør koden lettere å endre, gjenbruke og teste isolert: klassene kan utvikles og testes hver for seg.

Teknikk: Programmér mot grensesnitt i stedet for konkrete klasser, og bruk dependency injection – send inn avhengigheter via konstruktøren i stedet for å opprette dem inne i klassen. (Andre gyldige svar: Observer-mønsteret, eller å innføre et abstraksjonslag mellom klassene.)

Inntil 4 poeng. 2 poeng for en korrekt forklaring av kobling og hvorfor løs kobling er ønskelig, 2 poeng for én konkret og relevant teknikk (dependency injection, programmere mot grensesnitt, Observer e.l.).

Totalt: 60 poeng

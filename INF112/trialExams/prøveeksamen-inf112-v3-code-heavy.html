2 API-design

2.1 Design et API

Du skal designe et grensesnitt for en PathFinder som finner korteste vei mellom to punkter på et kart med hindringer.

  • a) Skissér grensesnittet (interface) med de metodene du mener er nødvendige. Tenk på: hva trenger klienten? Hva kan endres senere uten å ødelegge API-et?
  • b) Forklar dine designvalg – hvorfor valgte du akkurat disse metodene?

(1–2 avsnitt + kode)

a) Grensesnitt:

public interface PathFinder {
    /**
     * Finner korteste vei fra start til slutt.
     * @return en liste med posisjoner (start til slutt), eller tom liste hvis ingen vei finnes.
     */
    List<Position> findPath(Position start, Position goal);
    
    /**
     * Sjekker om en posisjon er gjennomsiktig (ikke hindring).
     */
    boolean isWalkable(Position pos);
}

b) Designvalg:

Jeg valgte å bare eksponere to metoder: findPath som er kjernefunksjonen, og isWalkable som er nyttig for validering. Jeg lot Position være et lite, uforanderlig objekt. Jeg returnerer en liste istedenfor en neste-node-iterator, fordi lista er enklere å bruke og teste. Jeg lar grensesnittet ikke vite om A*, Dijkstra eller andre algoritmer – det er implementasjonsdetalj.

Inntil 8 poeng. a) 4 poeng – grensesnitt skal være smalt og logisk. b) 4 poeng – skal begrunne valg (abstraksjon, uforanderlighet, enkelthet).

2.2 Fluent interface og builder

En QueryBuilder for å hente data fra en database skal kunne settes opp sånn:

List<User> result = new QueryBuilder(db)
    .from("users")
    .where("age > ?", 18)
    .where("country = ?", "Norway")
    .orderBy("name")
    .limit(10)
    .execute();
  • Skissér koden for QueryBuilder med minst from(), where(), og execute() metodene. Du trenger ikke implementere SQL-generering, bare skallet.

(1–2 avsnitt + kode)

public class QueryBuilder {
    private Database db;
    private String table;
    private List<String> whereClause = new ArrayList<>();
    private List<Object> parameters = new ArrayList<>();
    private String orderByClause = "";
    private int limitCount = -1;
    
    public QueryBuilder(Database db) {
        this.db = db;
    }
    
    public QueryBuilder from(String tableName) {
        this.table = tableName;
        return this;
    }
    
    public QueryBuilder where(String condition, Object... params) {
        whereClause.add(condition);
        for (Object p : params) {
            parameters.add(p);
        }
        return this;
    }
    
    public QueryBuilder orderBy(String column) {
        this.orderByClause = column;
        return this;
    }
    
    public QueryBuilder limit(int count) {
        this.limitCount = count;
        return this;
    }
    
    public <T> List<T> execute() {
        String sql = buildSQL();
        return db.query(sql, parameters);
    }
    
    private String buildSQL() {
        // implementasjon av SQL-generering
        return "";
    }
}

Nøkkelen er at hver metode returnerer this, slik at du kan kjede metodekall. Det gjør API-et lesbart og intuitivt.

Inntil 7 poeng. Skal vise fluent-prinsippet (hver metode returnerer this), og minst 3–4 metoder.

3 Kodeanalyse og designproblemer

3.1 Tight coupling

Se på denne koden:

public class PlayerController {
    private GameModel model;
    private SoundManager sounds;
    private ParticleSystem particles;
    
    public void handleAttack() {
        model.playerAttack();
        sounds.playSound("attack.wav");
        particles.createExplosion(model.getPlayerPos());
    }
    
    public void handleMove(int dx, int dy) {
        if (model.canMove(dx, dy)) {
            model.movePlayer(dx, dy);
        } else {
            sounds.playSound("blocked.wav");
        }
    }
}
  • a) Identifiser designproblemene i denne koden. Hva gjør den vanskelig å teste og å endre?
  • b) Foreslå en refaktorering. Skissér en bedre arkitektur.

(1–2 avsnitt + kode)

a) Designproblemer:

  • PlayerController er tett koblet til `SoundManager` og `ParticleSystem`. Hvis du vil teste `handleAttack`, må du mock alle tre.
  • Hvis du senere vil bytte lyd-implementasjon eller legge til vibrasjon, må du endre `PlayerController`.
  • Kontrolleren vet for mye – det er ikke bare input-håndtering, men også lyd- og effekt-logikk.

b) Bedre løsning – bruk Observer/Event-pattern:

public interface ActionListener {
    void onPlayerAttacked(Position pos);
    void onPlayerMoved(Position pos);
    void onMovementBlocked(Position pos);
}

public class PlayerController {
    private GameModel model;
    private List<ActionListener> listeners = new ArrayList<>();
    
    public void addListener(ActionListener listener) {
        listeners.add(listener);
    }
    
    public void handleAttack() {
        model.playerAttack();
        // notifiser alle lyttere
        for (ActionListener l : listeners) {
            l.onPlayerAttacked(model.getPlayerPos());
        }
    }
}

Nå kan SoundManager og ParticleSystem registrere seg som lyttere, uten at kontrolleren trenger å kjenne dem.

Inntil 8 poeng. a) 3 poeng – identifiser tight coupling og testability-problemer. b) 5 poeng – foreslå Observer eller lignende mønster.

3.2 Kodekvalitet

Se på denne metoden fra et `InventoryManager`:

public void addItem(String itemName, int quantity) {
    int max = 100;
    int current = 0;
    if (items.containsKey(itemName)) {
        current = items.get(itemName);
    }
    int newAmount = current + quantity;
    if (newAmount > max) {
        newAmount = max;
    }
    items.put(itemName, newAmount);
    System.out.println("Added " + quantity + " of " + itemName);
}
  • Identifiser minst tre kodelukter eller problemer i denne metoden, og foreslå forbedringer.

(1–2 avsnitt)

Problemer:

  • Magic number: `max = 100` er hardkodet. Det burde vært en konstant eller parameter.
  • Duplisert logikk: `items.get()` med sjekk kan erstattes med `getOrDefault()`.
  • Debug-utskrift: `System.out.println()` skal ikke være der. Bruk logging eller events.
  • Dårlig navn: `newAmount` er uklart – er det grunnmengden eller justert mengde?

Forbedret versjon:

private static final int MAX_STACK_SIZE = 100;

public void addItem(String itemName, int quantity) {
    int currentAmount = items.getOrDefault(itemName, 0);
    int cappedAmount = Math.min(currentAmount + quantity, MAX_STACK_SIZE);
    items.put(itemName, cappedAmount);
}

Inntil 7 poeng. Må identifisere minst 3 problemer og foreslå konkrete forbedringer.

3.3 Testability

Tenk på denne klassen – hvordan ville du testet `calculateDamage()` uten å starte et GUI-vindu?

public class CombatSystem {
    private Texture weaponTexture;
    private SpriteBatch batch;
    
    public int calculateDamage(Character attacker, Character defender) {
        int baseDamage = attacker.getAttackPower();
        int defense = defender.getDefense();
        int damage = Math.max(1, baseDamage - defense);
        batch.draw(weaponTexture, 0, 0); // tegn animasjon
        return damage;
    }
}
  • Identifiser testability-problemet og foreslå en løsning.

(1 avsnitt + kode-skisse)

Problem: `calculateDamage()` blander beregning med tegning. Du kan ikke teste den uten å starte et libGDX-vindu, fordi `batch.draw()` krever en aktiv GL-kontekst.

Løsning – separasjon av concerns:

public class CombatSystem {
    public int calculateDamage(Character attacker, Character defender) {
        int baseDamage = attacker.getAttackPower();
        int defense = defender.getDefense();
        return Math.max(1, baseDamage - defense);
    }
}

// En separat klasse for rendering
public class CombatRenderer {
    private SpriteBatch batch;
    private Texture weaponTexture;
    
    public void renderAttackAnimation() {
        batch.draw(weaponTexture, 0, 0);
    }
}

Nå kan du teste `calculateDamage()` som en ren enhetstests uten avhengigheter til grafikk.

Inntil 7 poeng. Må identifisere at grafikk og logikk er blandet, og foreslå separasjon.

4 Refaktorering og testing

4.1 Refaktorering

Her er en klasse som håndterer brukere:

public class UserManager {
    private List<User> users;
    
    public void addUser(String name, String email, int age, 
                        String country, String phone) {
        if (name == null || name.trim().isEmpty()) {
            System.out.println("Error: name required");
            return;
        }
        if (!email.contains("@")) {
            System.out.println("Error: invalid email");
            return;
        }
        if (age < 18 || age > 120) {
            System.out.println("Error: age out of range");
            return;
        }
        User u = new User(name, email, age, country, phone);
        users.add(u);
        System.out.println("User added");
    }
}
  • a) Identifiser designproblemer og foreslå refaktorering.
  • b) Skissér den refaktorerte koden.

(1–2 avsnitt + kode)

a) Problemer:

  • Validering er blandet med oppretting og lagring.
  • System.out-utskrifter i logikk-kode.
  • Mange parametere – kunne brukt en builder eller config-objekt.
  • Ingen exception-håndtering – feil bare skrives ut.

b) Refaktorering:

public class UserValidator {
    public void validate(UserData data) throws ValidationException {
        if (data.getName() == null || data.getName().trim().isEmpty()) {
            throw new ValidationException("name required");
        }
        if (!isValidEmail(data.getEmail())) {
            throw new ValidationException("invalid email");
        }
        if (data.getAge() < 18 || data.getAge() > 120) {
            throw new ValidationException("age out of range");
        }
    }
    
    private boolean isValidEmail(String email) {
        return email != null && email.matches("[^@]+@[^@]+");
    }
}

public class UserManager {
    private List<User> users;
    private UserValidator validator;
    
    public void addUser(UserData data) throws ValidationException {
        validator.validate(data);
        User u = new User(data);
        users.add(u);
    }
}

Inntil 10 poeng. a) 4 poeng – identifiser 3+ problemer. b) 6 poeng – skal vise separasjon av concerns (validator, manager, data-objekt) og bruk av exceptions.

4.2 Testing-strategi

Skriv JUnit-tester for den refaktorerte `UserValidator` fra oppgave 4.1. Fokuser på:

  • Gyldige data
  • Manglende navn
  • Ugyldig e-post
  • Ugyldig alder (for ung/for gammel)

(1–2 avsnitt + kode)

public class UserValidatorTest {
    private UserValidator validator = new UserValidator();
    
    @Test
    public void testValidUser() throws ValidationException {
        UserData data = new UserData("John", "john@example.com", 30, "", "");
        // Skal ikke kaste exception
        validator.validate(data);
    }
    
    @Test
    public void testMissingName() {
        UserData data = new UserData("", "john@example.com", 30, "", "");
        assertThrows(ValidationException.class, () -> validator.validate(data));
    }
    
    @Test
    public void testInvalidEmail() {
        UserData data = new UserData("John", "notanemail", 30, "", "");
        assertThrows(ValidationException.class, () -> validator.validate(data));
    }
    
    @Test
    public void testAgeOutOfRange_TooYoung() {
        UserData data = new UserData("John", "john@example.com", 15, "", "");
        assertThrows(ValidationException.class, () -> validator.validate(data));
    }
    
    @Test
    public void testAgeOutOfRange_TooOld() {
        UserData data = new UserData("John", "john@example.com", 130, "", "");
        assertThrows(ValidationException.class, () -> validator.validate(data));
    }
}

Jeg testet både gyldige og ugyldige tilfeller, med fokus på grensekasser (18, 120) som ofte er kilder til bugs.

Inntil 10 poeng. Skal dekke alle fire kravene med meningsfulle asserts. Bonus for grensekasse-testing.

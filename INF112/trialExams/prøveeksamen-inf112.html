1 Prosjektrefleksjon

1.1 Design og vedlikehold

Tenk tilbake på arkitektur og design av prosjektet ditt.

  • Var det noen deler av koden som ble særlig vanskelige å endre eller vedlikeholde? Forklar kort hva som gjorde det vanskelig, og vilket design-prinsipp eller mønster kunne ha hjulpet.

(1–2 avsnitt)

Eksempel på god refleksjon:

Et vanlig problem var at input-håndtering var tett koblet til modelllogikk. F.eks. hvis `GameController` kalte `model.movePlayer()` direkte, og senere ville man bytte input-kilde (fra tastetrykk til nettverk), måtte man endre både kontroller og modell. Dette bryter Dependency Inversion Principle. En bedre løsning hadde vært å bruke ett Command-pattern eller observer-pattern, slik at modellen ikke vet hvordan input kommer, bare at det har skjedd en handling.

Alternativt: En klasse som både tegnet grafikkk og oppdaterte posisjoner var vanskelig å teste. Med Model-View-Controller-separasjon, der modellen ikke kjente til grafikk, kunne man testet `move()`-logikken uten å starte et vindu.

Inntil 5 poeng. Kriterier: Identifiserer ett konkret design-problem (ikke bare "det var dårlig"), foreslår ett relevant prinsipp/mønster, og forklarer hvorfor det ville hjulpet.

2 Verktøy og prosess

2.1 API-design

Tenk på et API eller grensesnitt i prosjektet ditt (f.eks. en `GameMap`, `AudioManager`, `PathFinder` eller en custom interface du laget).

  • Beskriv grensesnittet kort og forklar hvilke designvalg du gjorde. Hvorfor var de gode valg?

(1–2 avsnitt)

Eksempel:

Vår `GameMap` grensesnitt eksponerte kun tre metoder: `getTileAt(x, y)`, `isWalkable(x, y)` og `getWidth()`. Dette var et bevisst valg for å gjøre det enkelt for andre moduler å bruke kartet uten å kjenne implementasjon. Vi valgte ikke å eksponere intern representasjon (f.eks. en 2D array), fordi det gjorde det lett å senere bytte fra array til en hash-map eller en komprimert format.

Vi valgte også å la kartet være uforanderlig fra brukerens perspektiv – kun `GameLogic` kunne endre det. Dette unngikk utilsiktede endringer fra flere deler av koden samtidig.

Inntil 4 poeng. Søker konkret API-eksempel med begrunnelse for designvalgene. Gode svar nevner smale grensesnitt, abstraksjon eller uforanderlighet.

2.2 Git og samarbeid

  1. Beskriv kort hvordan ditt team organiserte arbeid på Git. Brukte dere feature branches, personlige branches, eller noe annet?
  2. En ny utvikler skal starte i et team som bruker GitLab med merge requests. Forklar kort hvorfor merge requests er nyttige for teamsamarbeid.

(1–2 avsnitt til sammen)

a) Eksempel:

Vi brukte feature branches – en ny branch for hver større oppgave eller bug-fix, f.eks. `feature/pathfinding-ai` eller `fix/collision-detection`. Vi holder brancher kortlivede (1–3 dager) for å unngå store merge-konflikter. Hver branch jobbet én person, eller to personer jobbet sammen på samme branch.

b) Merge requests:

Merge requests gjør det enkelt å gjennomgå kode før den blir en del av main. En annen person i teamet godkjenner endringene, og kan kommentere eller spørre om avklaringer. Dette sikrer at flere har sett koden, og det er enklere å fange bugs og designfeil før de forplanter seg. CI kjører også tester automatisk på merge-request-koden, så du vet at den minst bygger før du merger.

Inntil 5 poeng. a) 2 poeng – beskriv branching-strategi. b) 3 poeng – merge requests skal knyttes til kodegjennomgang, CI og kvalitet, ikke bare "det holder oversikt".

2.3 Refaktorering og tester

Forklar kort: Når og hvorfor kan det være nyttig å refaktorere kode som allerede fungerer?

(1 avsnitt)

Refaktorering endrer struktur uten å endre atferd. Det er nyttig når koden blir vanskelig å forstå eller vedlikeholde – hvis du senere skal legge til ny funksjonalitet, blir det mye lettere hvis koden er tydelig og godt organisert. Refaktorering "betaler ned technical debt" tidlig, så den ikke blir til et stort problem senere.

Videre, hvis du har gode tester, er refaktorering trygt – testene sikrer at du ikke har ødelagt noe. Hvis du venter til slutten av prosjektet med refaktorering, er det både dyrere og mer risikabelt.

Inntil 4 poeng. Søker forståelse for at refaktorering er investering i fremtidig vedlikehold, og at tester gjør det trygt.

3 Arkitektur og design

3.1 Model-View-Controller

Se for deg følgende kode:

public class GameMap {
    private int[][] tiles;
    private Texture mapTexture;
    
    public void render(SpriteBatch batch) {
        // tegn kartet
        batch.draw(mapTexture, 0, 0);
    }
    
    public boolean canWalkOnTile(int x, int y) {
        return tiles[x][y] != WALL;
    }
    
    public void update(float delta) {
        // oppdater karttilstand, håndter animasjoner osv
    }
}
  • a) Identifiser designproblemet: Hva er galt med denne klassen fra et MVC-perspektiv? Forklar kort.
  • b) Foreslå en bedre løsning: Skissér hvordan du ville omstrukturert koden.

(2 avsnitt)

a) Designproblem:

Klassen blander modell (karrdata og logikk som `canWalkOnTile`) med visning (tegning med `SpriteBatch` og `Texture`). Dette gjør at:

  • Du kan ikke teste `canWalkOnTile` uten et grafikk-bibliotek.
  • Hvis du senere vil tegne kartet annerledes, eller støtte flere visningsformat, må du endre modelklassen.
  • Koden er tett koblet til libGDX, som gjør den vanskelig å gjenbruke i f.eks. en CLI-versjon eller et nettspill.

b) Bedre løsning:

// Modell – ren Java, ingen grafikk
public interface GameMap {
    boolean canWalkOnTile(int x, int y);
    int getWidth();
    int getHeight();
    int getTileType(int x, int y);
}

// Visning – tegner kartet
public class MapRenderer {
    private GameMap map;
    private Texture mapTexture;
    
    public void render(SpriteBatch batch) {
        batch.draw(mapTexture, 0, 0);
    }
}

Nå er modellen separat fra tegningen, så du kan teste og endre den uavhengig.

Inntil 7 poeng. a) 3 poeng – må identifisere at modell og visning er blandet, og forklare hvorfor det er dårlig. b) 4 poeng – må foreslå en separasjon (grensesnitt for modell, egen klasse for rendering).

3.2 SOLID og design-mønstre

Se for deg at du skal implementere forskjellige typer av fiender i et spill: `Zombie`, `Orc`, `Dragon`. Hver fiendtype har sin egen `attack()`-metode.

En dårlig løsning ville vært:

public class Combat {
    public void executeAttack(Object enemy) {
        if (enemy instanceof Zombie) {
            Zombie z = (Zombie) enemy;
            z.attack();
        } else if (enemy instanceof Orc) {
            Orc o = (Orc) enemy;
            o.attack();
        } else if (enemy instanceof Dragon) {
            Dragon d = (Dragon) enemy;
            d.attack();
        }
    }
}
  • a) Hvilket SOLID-prinsipp brytes? (navngi det)
  • b) Forklar kort hvorfor det er et problem, og hva som skjer hvis du legger til en ny fiendtype.
  • c) Foreslå en bedre løsning – hva ville du gjort i stedet?

(1–2 avsnitt)

a) SOLID-prinsipp: Open-Closed Principle (OCP) – klassen er lukket for utvidelse (du må redigere den hver gang du legger til en ny fiendtype).

b) Problemet: Når du legger til en ny fiendtype (f.eks. `Goblin`), må du åpne `Combat`-klassen og legge til en ny `else if`-branch. Dette øker risiko for bugs og gjør koden skjør.

c) Bedre løsning – bruk polymorfi eller et grensesnitt:

public interface Enemy {
    void attack();
}

public class Combat {
    public void executeAttack(Enemy enemy) {
        enemy.attack();  // Polymorfi – vet ikke type, men det spiller ingen rolle
    }
}

Nå er koden åpen for utvidelse – du kan legge til nye fiendtyper uten å endre `Combat`.

Inntil 6 poeng. a) 1 poeng – må identifisere OCP. b) 2 poeng – må forklare problemet og hva som skjer ved utvidelse. c) 3 poeng – må foreslå grensesnitt/polymorfi som løsning.

3.3 Abstraksjon og avhengigheter

Forklar kort: Hva er fordelen med å bruke et grensesnitt (interface) fremfor en konkret klasse når du deklarerer variabler eller parametere?

(1 avsnitt)

Når du deklarerer med et grensesnitt (`List<String> list` i stedet for `ArrayList<String> list`) eller tar inn et grensesnitt som parameter (`void process(AudioPlayer player)` i stedet for `void process(SpeakerAudioPlayer player)`), gjør du koden fleksibel – du kan senere bytte implementasjon uten å endre koden som bruker det.

F.eks. hvis du senere lager `HeadlessAudioPlayer` for testing, kan `GameLogic` fortsatt ta inn `AudioPlayer`-grensesnittet, og jobben er enkel.

Videre gjør det testing enklere – du kan lage en mock-implementasjon av grensesnittet for testformål.

Inntil 5 poeng. Søker forståelse for fleksibilitet, substituering av implementasjoner og testbarhet.

4.2 Kodelukt og vedlikehold

Se på denne (utenktes) koden fra et AI-system:

public void decideAction() {
    if (health < 30) {
        flee();
    } else if (health < 50 && ammo < 10) {
        retreat();
    } else if (health > 70 && seeEnemy()) {
        attack();
    } else if (ammo > 50) {
        hunt();
    } else {
        patrol();
    }
}
  • a) Identifiser ett eller to kodelukt-tegn i denne metoden.
  • b) Forklar kort hvorfor det er et problem, og hvordan du ville forbedret det.

(1–2 avsnitt)

a) Kodelukter:

  • Magic numbers: Tallene (30, 50, 70, 10, 50) er hardkodet. Hvis du senere vil justere AI-vanskelighetsgrad, må du redigere koden.
  • For lang metode med kompleks logikk: Metoden gjør mange ting (bestemmer strategi basert på mange betingelser). Det er vanskelig å teste og å forstå.

b) Forbedringer:

public class AIThresholds {
    static final int FLEE_HEALTH = 30;
    static final int RETREAT_HEALTH = 50;
    static final int HUNT_AMMO = 50;
}

public void decideAction() {
    if (shouldFlee()) attack();
    else if (shouldRetreat()) retreat();
    else if (shouldAttack()) attack();
    else if (shouldHunt()) hunt();
    else patrol();
}

private boolean shouldFlee() {
    return health < AIThresholds.FLEE_HEALTH;
}

Nå er magiske tall navngitt, og hver betingelse er en metode som er lett å forstå og teste.

Inntil 5 poeng. a) 2 poeng – må identifisere minst ett kodelu tegn. b) 3 poeng – må foreslå konkret forbedring (navngitte konstanter, små metoder osv).

4.3 Lisenser og ansvar

Se for deg at du skal publisere koden fra semesterprosjektet på GitHub eller GitLab.

  • a) Hvilke ressurser eller biblioteker bør du dokumentere, og hvorfor?
  • b) Hva er forskjellen mellom opphavsrett og lisens, og hvorfor er det viktig å vite?

(1–2 avsnitt)

a) Ressurser som bør dokumenteres:

  • Biblioteker og dependencies (LibGDX, JUnit, Mockito osv.) – hvilke lisenserhar de? Hvis noen bruker GPL, må ditt prosjekt kanskje være åpen kildekode.
  • Grafikk og lyd – hvis du bruker kunstnerisk arbeid fra nett, hvem laget det, og hvilken lisens? Du må kreditere forfatteren.
  • Ikoner, fonter, datasets – samme regel.

b) Opphavsrett vs. lisens:

Opphavsrett er automatisk – når du lager noe, eier du automatisk opphavsretten. Du bestemmer hvem som får lov til å kopiere eller endre det. Lisens er den eksplisitte tillatelses du gir. F.eks. en MIT-lisens sier "du får lov til å bruke, endre og distribuere denne koden." Hvis du ikke legger ved en lisens, har andre ikke formelt tillatelses til å bruke koden din, selv om den er på GitHub.

Inntil 5 poeng. a) 2 poeng – må nevne minst to typer ressurser. b) 3 poeng – må forklare at opphavsrett er automatisk, og at lisens gir eksplisitt tillatelse.
